# Optional presentation-package protocol

> **Purpose:** Describe the optional versioned handoff record emitted with a passed HTML presentation package.
>
> **Trigger:** Use when a downstream consumer needs to inspect or validate the package without importing this Skill at runtime.
>
> **Prereqs:** A package directory generated by this Skill and, for acceptance, a passed core validation status and QA report.
>
> **Next:** [review-and-delivery.md](review-and-delivery.md)
>
> **Contract:** The core record is `pptx-creator.presentation-package` version `1.0.0`; the Text-to-HTML extension is optional evidence.

## Core protocol 1.0

`presentation-package.json` uses the frozen core contract:

```json
{
  "protocol": "pptx-creator.presentation-package",
  "version": "1.0.0"
}
```

The core protocol remains `1.0.0` for this Skill. Text-to-HTML Plan 2.0 does not change that protocol version.

This Skill emits `kind: "html-presentation"`, producer `text-to-html`, `entrypoint: "index.html"`, a 1280×720 deck, ordered stable slide IDs, source-bound component geometry, local assets, validation reports, degradations, and feature flags. The canonical core schema is bundled at `schemas/presentation-package.schema.json`; local validation is implemented by `scripts/validate-presentation-package.mjs`.

The protocol is an optional versioned handoff, not a Codex manifest and not a runtime dependency on `html-to-pptx` or `image-to-pptx`.

Core consumers must:

- reject unsupported `protocol` or core `version` with `E_PROTOCOL_ID` or `E_PROTOCOL_VERSION`;
- resolve every core path below the package directory and reject traversal, absolute paths, symlinks, and missing required package resources;
- preserve slide order, IDs, dimensions, notes, sources, assets, z-order, and `editableIntent`;
- treat `validation.status !== "passed"` as unaccepted input;
- honor `degradations` and never silently claim lost editability.

The source plan is the content authority; computed browser geometry in the core protocol is the rendered-HTML authority.

## Responsibility boundary

The producer deterministically records package paths, geometry, assets, validations, degradations, and optional extension evidence. A consumer validates only the declared protocol and its package-local resources; it does not infer a missing approval, promote a failed package, or turn this handoff into a dependency on another Skill.

## Optional Text-to-HTML extension

Text-to-HTML may place the following optional extension inside the core protocol's `extensions` object:

```json
{
  "extensions": {
    "pptx-creator.text-to-html/v2": {
      "version": "2.0.0",
      "plan": {
        "version": "2.0.0",
        "canonicalInputSha256": "<sha256>",
        "reviewStatus": "approved"
      },
      "reports": {
        "sourcePlan": { "path": "presentation-plan.source.json", "sha256": "<sha256>" }
      }
    }
  }
}
```

The extension is optional and does not alter any core 1.0 field or validation rule. A core-only consumer may validate and consume the 1.0 package while ignoring this extension. An extension-aware consumer opts in to the additional Text-to-HTML evidence checks.

`plan` records the accepted Plan 2.0 version, the canonical-input SHA-256, and the current review status. The canonical-input digest is a content binding, not permission to rewrite a plan after approval.

Each `reports` value has a package-relative `path` and SHA-256. The emitted extension names these immutable evidence artifacts:

| Report key | Artifact |
|---|---|
| `sourcePlan` | `presentation-plan.source.json` |
| `canonicalPlan` | `presentation-plan.json` |
| `designIntent` | `design-intent.json` |
| `contentBudget` | `content-budget-report.json` |
| `narrative` | `narrative-report.json` |
| `review` | `review-report.json` |
| `assetLedger` | `asset-ledger.json` |
| `license` | `license-report.json` |
| `provenance` | `provenance.json` |
| `visualScorecard` | `visual-scorecard.json` |
| `notice` | `NOTICE` |

The deterministic visual scorecard evaluates the QA, narrative, pagination, and provenance reports; it is extension evidence, not a replacement for Host visual acceptance. An extension-aware consumer must verify each declared relative path and hash before relying on its plan, review, asset, rights, provenance, or scorecard claims. It must preserve the reports as immutable evidence and must not use an extension to promote a pending or failed core package to accepted status.

Unknown extension names remain isolated inside `extensions`; they do not license unknown top-level fields or an unsupported core protocol version.
